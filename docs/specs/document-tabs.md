# Document tabs: several documents of both modes open in tabs

## Context

Pincel holds one document at a time: New, Open, Open Recent, a file drop or Paste as New Image replace the open document (after the unsaved-changes prompt). The owner wants several images open side by side in tabs, as in paint.net. The first version kept tabs within one mode; on 2026-11-04 the owner changed the plan: **tabs mix both modes** — one tab bar holds Pixel and Image documents side by side, and opening a document never replaces the others.

Decision Log 2026-11-04 ("Tabs mix both modes", superseding "Several documents per editor") records the architecture: each mode's editor holds the tabs of its mode as before; at most one editor per mode is mounted, only the editor of the active tab is visible, and a mode's editor and wasm module load with its first document and are released with its last. It amends 2026-09-06 ("Two cores, one shell"), whose session holds one document in one editor.

This spec builds on `unsaved-changes-prompt` (Save / Don't Save / Cancel) and extends it to several documents, as that spec's out-of-scope list announces.

**Terms.** *Tab*: one open document in the tab bar, with its own content, undo history, file (name, location, format), unsaved state, view (zoom, scroll), selection and — in Pixel mode — current layer, frame and onion-skin state. *Active tab*: the tab whose document the canvas, panels, menus and status bar show. *Session*: all open tabs of both modes, with at most one mounted editor per mode. *A document's mode*: given by its format as today (`.aseprite` → Pixel; PNG / JPEG / WebP / BMP / GIF / TIFF / ORA → Image), with two exceptions: File ▸ Open… while a Pixel tab is active opens a PNG as a Pixel tab (Pixel mode's own Open, as today), and Paste as New Image opens a tab of the active tab's mode. *Loaded mode*: a mode whose editor is mounted; *released*: the mode's editor is unmounted and its documents freed, while its already downloaded wasm module stays in the page, so a later document of that mode needs no new download. *Tab bar*: one list of tabs for the whole session; each mode's editor shows it at the same place, and its horizontal scroll position is kept across mode switches. *Unsaved changes* and *document name*: as `unsaved-changes-prompt` defines them, per tab. *Shared state*: the active tool and its options, the foreground / background colours (RGBA values), the panel layout and the sidebar width — one per mode, shared by that mode's tabs and unchanged when the active tab changes; each Pixel tab keeps its own palette, which is document content. *Keys*: chords are written with the Windows / Linux names; on macOS Ctrl means ⌘ Command and Alt means ⌥ Option (the `mod` convention of `ui/src/lib/shell/shortcuts.ts`) unless the tab-key table below says otherwise. *Same file*: in the desktop app, the same file path (compared case-insensitively on Windows and macOS, exactly on Linux, without resolving links); in the browser, two file handles the File System Access API reports as the same entry; a document without a path or handle (never saved, or opened through the download fallback) is never the same file as another.

## Scope

### In scope

- A tab bar in both editors; opening, creating, switching, closing tabs with pointer and keyboard
- One tab bar for documents of both modes; switching to a tab of the other mode shows that mode's editor
- New, Open, Open Recent, file drop, Paste as New Image and files handed over by the operating system: every document opens as a new tab, of its own mode, without a prompt
- Per-tab document state; tool and colour state shared per mode
- The unsaved-changes prompt for one tab (closing it) and for several tabs (closing the desktop window)
- Autosave per tab; recovery offers the snapshots of both modes and recovers into tabs
- Loading a mode's editor and wasm module only when its first document opens
- Top bar and window title follow the active tab
- en + de strings
- Revision of `app-shell` AC-08, AC-13 and AC-16, `autosave-recovery` AC-04 and AC-05, and `unsaved-changes-prompt` AC-01

### Out of scope

- Converting a tab to the other mode, or dragging layers between a Pixel and an Image tab — because the two modes have different document models; copy / paste through the clipboard (PNG) works across modes, and mode conversion is a backlog item
- Reordering tabs by drag, tearing a tab off into its own window, split views — because they are layout features beyond "several images open"; paint.net 5 has no split view either
- Reopening the tabs of the last session on start — because the recovery covers unsaved work, and remembering saved files is Open Recent's job
- Copying layers or frames between tabs by drag — because copy / paste across tabs already works through the clipboard (`copy-cut-paste`)
- A limit on the number of tabs — because memory depends on document sizes, not on a count (see Assumptions for what running out of memory means)

## Acceptance criteria

- [x] AC-01 (always): While at least one document is open, a tab bar between the options bar and the canvas shows one tab per open document of either mode, in the order they were opened, each with a mode marker (the Pixel or Image icon, with the mode in its accessible name), the document name, an unsaved marker while it has unsaved changes and a close button; the active tab is visually marked and exposed as the selected tab — at window widths of 1280, 800 and 390 px, where the bar scrolls horizontally when the tabs do not fit and scrolls the active tab into view.
- [x] AC-02 (event): When the user opens, creates (File ▸ New… with either mode), recovers, drops, receives from the operating system or pastes as new image a document of either mode, then it opens as a new tab of its mode after the last tab and becomes the active tab; every other tab, of either mode, keeps its document, undo history and unsaved state, and no unsaved-changes prompt appears.
- [x] AC-03 (event): When the user opens (Open, Open Recent, drop, operating system) the same file as an open tab of either mode, then that tab becomes active, no second tab opens and that tab's unsaved changes are kept. A recovered snapshot always opens as a new tab, because it holds edits the file does not.
- [x] AC-04 (event): When the user clicks a tab, or presses a next / previous tab shortcut from the tab-key table, then that tab becomes active, wrapping from the last to the first and back across both modes; the canvas, layers, timeline (Pixel), palette (Pixel), status bar, undo / redo state, top-bar name, mode badge and window title show the newly active document, and when it is of the other mode, the menus, tool rail, options bar and panels become that mode's.
- [x] AC-05 (always): Each tab keeps its own view and selection: after switching away — also to a tab of the other mode — and back, the zoom, the scroll position, the selection and, in Pixel mode, the current layer, current frame and onion-skin settings are as they were. The active tool, its options and the colours are shared by the tabs of one mode and stay as they are when switching; each mode keeps its own, so switching from a Pixel tab to an Image tab and back restores the Pixel tool and colours.
- [x] AC-06 (event): When the user undoes or redoes, then only the active tab's history changes; edits in one tab never change another tab's document.
- [x] AC-07 (event): When the user closes a tab without unsaved changes (its close button, a middle-click on the tab, File ▸ Close, or a close shortcut from the tab-key table), then the tab disappears and the tab to its right becomes active, whatever its mode (the one to its left when it was the last) — as in browsers and paint.net.
- [x] AC-08 (event): When the user closes a tab with unsaved changes, then the unsaved-changes prompt of `unsaved-changes-prompt` asks about that document (Save / Don't Save / Cancel, with its name); Save saves it and closes the tab only after a successful save, Don't Save closes it, Cancel keeps it; while the prompt is open the tab being closed is the active tab, its mode's editor shown.
- [x] AC-09 (event): When the last tab is closed, then the start screen is shown; when the last tab of one mode is closed while tabs of the other mode remain, then the next tab (AC-07) becomes active and that mode's editor is released (AC-16).
- [x] AC-10 (event): When the desktop window is closed (or the app quits) and exactly one tab has unsaved changes, then the window stays open, that tab becomes active (its mode's editor shown) and the single-document prompt of `unsaved-changes-prompt` asks about it.
- [x] AC-11 (event): When the desktop window is closed (or the app quits) and two or more tabs, of either mode, have unsaved changes, then one prompt lists the names of all of them and offers Save All, Don't Save and Cancel (Save All has focus, Escape cancels); Save All saves them one after another in tab order, left to right, each tab becoming active while it saves (a never-saved document asks for its location as File ▸ Save does) and closes the app only when every save succeeded; if a save is cancelled or fails, the close is aborted, documents saved so far stay saved, and the rest keep their unsaved changes; Don't Save closes the app and discards them all; Cancel changes nothing.
- ~~AC-12 (event): When the action replaces the session after the prompt (or without one when no tab has unsaved changes), then all tabs clos…~~ dropped: no action replaces the session any more since tabs mix both modes (AC-02); closing the desktop window is AC-10 / AC-11.
- [x] AC-13 (always): The shell's notion of unsaved changes — the browser's leave-page warning (`app-shell` AC-15) and the desktop close prompt — counts the session as unsaved while any tab has unsaved changes.
- [x] AC-14 (state): While several tabs have unsaved changes, each is autosaved on its own (as `autosave-recovery` AC-01 – AC-03 describe for one document), and a save or a Don't Save on one tab removes only that tab's snapshot.
- [x] AC-15 (event): When the first editor starts in a page load and snapshots of either mode exist, then the recovery dialog lists them all; when the user clicks Recover on one, that document opens as a new tab of its mode (loading that mode's editor if needed, AC-22), marked unsaved, and the dialog stays open while snapshots remain; recovering several gives several tabs.
- [x] AC-16 (always): Closing a tab releases its document, and closing the last tab of a mode releases that mode's editor: a diagnostic count of open documents, which each mode's wasm module exposes for tests and which stays readable after release (the module stays in the page), equals the number of open tabs of that mode after any sequence of opening and closing tabs, and is 0 once that mode has no tab.
- [x] AC-17 (state): While a tab has a running save, closing that tab by any means of AC-07 does nothing, and other tabs of either mode can be switched to; closing the desktop window waits for the running save to finish and then prompts as AC-10 / AC-11 describe (as `unsaved-changes-prompt` AC-10 does for one document).
- [x] AC-20 (always): Every tab shortcut works with the keys of the tab-key table for the platform it runs on, and the hints in menus and tooltips name them as that platform does (on macOS with ⌃ ⌥ ⇧ ⌘ symbols, e.g. File ▸ Close shows ⌘W in the desktop app); on macOS the shortcuts match the physical key, so ⌥W closes the tab although the keyboard layout turns it into another character.
- [x] AC-19 (event): When the user drops several files at once, then each file opens as a tab of its own mode, in drop order (AC-02 / AC-03 for each); unreadable or unsupported files are skipped and one notice names how many.
- [x] AC-21 (always): Only the editor of the active tab is visible and receives keyboard shortcuts, menu commands (including the desktop app's native menu), pointer input and clipboard events; the other mode's editor, while it stays mounted in the background, reacts to none of them, and its tabs keep their documents exactly (content, undo history, view, selection).
- [x] AC-22 (always): A session that never opened a document of a mode never downloads that mode's wasm module; a mode's editor mounts when its first document of the session opens (again after a release, without a new download), and switching between tabs of two loaded modes remounts neither editor and reloads no document.
- [x] AC-23 (error): If a mode's editor or wasm module fails to load (offline web app, a failed download or compile), then an error notice names the document that could not be opened, no tab opens for it, and every open tab and the active tab stay as they were.
- [x] AC-24 (state): While a mode's editor is loading for a document, the open tabs stay usable and can be switched; further documents that arrive meanwhile (drop, Open, OS hand-over) open after it, in the order they arrived.
- [x] AC-25 (event): When a save of a tab that is no longer active fails (a running save, after the user switched to a tab of either mode), then the error is shown at once as a notice naming the document, and that tab keeps its unsaved marker.
- [x] AC-18 (option): Where the UI language is German, the tab bar's labels (close button, accessible names), the several-documents prompt and File ▸ Close are German ("Schließen", „Ungespeicherte Änderungen in {n} Bildern“, „Alle speichern“, „Nicht speichern“, „Abbrechen“).

## Tab keys

| Action | Windows / Linux desktop | macOS desktop | Web build, Windows / Linux | Web build, macOS |
| ------ | ----------------------- | ------------- | -------------------------- | ---------------- |
| Next tab | Ctrl+Tab, Alt+Page Down | ⌃Tab (Control, because ⌘Tab is the system app switcher), ⇧⌘], ⌥⇟ | Alt+Page Down | ⌥⇟ (fn+⌥↓ on keyboards without Page Down) |
| Previous tab | Ctrl+Shift+Tab, Alt+Page Up | ⌃⇧Tab, ⇧⌘[, ⌥⇞ | Alt+Page Up | ⌥⇞ |
| Close tab | Ctrl+W, Alt+W | ⌘W, ⌥W | Alt+W | ⌥W |

The web build gets no Ctrl / ⌘ tab chords because the browser keeps Ctrl+Tab, Ctrl+W, ⌘W and ⇧⌘[ / ] for its own tabs. On macOS the desktop app's native menu owns ⌘W (File ▸ Close) as it owns its other accelerators (pincel.md §9.4).

## Technical notes

Hints, not contracts — paths drift; grep for the names (verified 2026-11-04).

- Shell: `ui/src/App.svelte` (guard, `launch`), `ui/src/lib/shell/session.svelte.ts` (`session.dirty` is one flag today, `launch` remounts via `seq`), `lib/shell/types.ts` (`EditorProps`: `onDirtyChange`, `onOpenFile`, `onOpenForeign`, `onOpenRecent`). Routing has to reach the editor of the document's mode — mounting it on demand through the existing dynamic `import()` — instead of `launch`; both editors' module-level stores already survive mounting side by side, the window-level key / menu / paste listeners need an "active" gate (AC-21).
- Image mode: the core is handle-based (`pincel-image-wasm`), so several documents already fit; module singletons that assume one document: `modes/image/stores/editor.svelte.ts` (`editor.handle`), `modes/image/core/document-file.ts`, `controller.newDocument` / `openBytes` (they close the previous handle). `ImageEditor` unmount does not close the handle today (AC-16 fixes the leak).
- Pixel mode: `Document` is a per-instance wasm class; per-tab state lives in `modes/pixel/stores/editor.svelte.ts` (`ed.doc`, file, view) and `file-ops.ts` / `doc-ops.ts`.
- Autosave: `lib/idb/autosave-session.svelte.ts` (`AutosaveSession`, one `docId` per document; `close()` deletes the snapshot). One session per tab.
- Shortcuts: `lib/shell/shortcuts.ts` (`mod` = Ctrl or ⌘, `chordLabel` prints ⇧⌘S on macOS). ⌃Tab on macOS needs a real Control chord, not `mod`. On macOS ⌥ letters produce other characters (⌥W types "∑"), so match these chords on `KeyboardEvent.code`, not `key`.
- A tab bar component under `lib/components/layout/` shared by both editors via `EditorFrame`.

## Edge cases

| Scenario | Expected behavior |
| -------- | ----------------- |
| Pixel mode opens a PNG through its own Open | It opens as a Pixel tab (as today) |
| Copy in a Pixel tab, Paste in an Image tab | Works through the clipboard as a PNG, as between two documents today |
| A Pixel tab and an Image tab with the same document name | Both show the name; the mode marker tells them apart |
| The same untitled name twice (two new documents) | Both tabs read the default name; they are separate documents |
| An effect panel or other dialog is open and the user clicks another tab | Tab switching is blocked while a dialog is open, as other editor input is |
| Several dirty tabs, Save All, the second document's Save As is cancelled | The first stays saved, the second and later stay unsaved, the action is aborted (AC-11) |
| A tab's file is a recent entry that is opened again from Open Recent | The existing tab becomes active (AC-03) |
| Closing a tab while an autosave write of it is running | The tab closes; its snapshot is removed when the write finishes |
| Opening a document fails (unreadable file) | An error is shown; no tab opens and the active tab stays |
| The other mode's editor or wasm fails to load | AC-23: a notice, no new tab, all tabs stay |
| A file is dropped or handed over while an unsaved-changes prompt is open | It is not opened; a notice says it was ignored because a prompt was open |
| Save All with unsaved tabs of both modes | Each tab becomes active in turn (its mode's editor shown) while it saves, in tab order |

## Assumptions

| Assumption | Reason | Risk |
| ---------- | ------ | ---- |
| Closing the last tab shows the start screen | The start screen is the "no document" state the shell already has | Low |
| Tool and colours are shared per mode, per-tab state is document state | paint.net shares tools and the palette across images; the two modes have different tool sets, so sharing tools is impossible; colours stay per mode too because Pixel mode stores its colours with its own prefs and palette (`autosave-recovery` AC-12) | Low |
| Both editors stay mounted while both modes have tabs | Switching keeps every editor's state without re-creating it; costs the memory of the second wasm module (each module has its own wasm memory) | Medium: two large documents of different modes use two memories |
| The several-documents prompt is a list with Save All / Don't Save / Cancel, not one prompt per tab | paint.net and Office show one list for many documents; one decision is faster than n prompts | Low |
| Alt+Page Up / Down and Alt+W in the web build | Browsers reserve Ctrl+Tab and Ctrl+W | Medium: Alt+W may collide with a browser or OS shortcut on some systems; the tab close button and File ▸ Close remain |
| No tab limit | All tabs of a mode share one wasm memory (at most what the browser grants, below the wasm32 limit of 4 GB); running out of it ends the whole editor, not one tab, and the autosave recovery is the safety net — the same as one huge document today | Medium |

## Summary

> Completed: 2026-11-05

- One tab bar for Pixel and Image documents (`lib/components/layout/TabBar.svelte` via `EditorFrame`): mode marker, unsaved marker, close button, horizontal scroll shared across both editors' bars.
- Every way in (New, Open, Open Recent, drop of one or several files, OS hand-over, Paste as New Image, Recover) opens a new tab of its mode without a prompt; the same file activates its existing tab across modes.
- Per-tab document, history, file, view and selection behind the existing stores (`lib/shell/tab-store.ts`); tools and colours shared per mode; at most one editor per mode mounted, the inactive one hidden and inert, loaded with its mode's first document and released with its last.
- Unsaved-changes prompt per tab on close, a Save All / Don't Save / Cancel list when the desktop window closes with several unsaved tabs, autosave and recovery per tab across both modes, platform tab keys (desktop File > Close with CmdOrCtrl+W).
- Open-document diagnostics in both wasm cores (`document_count`, `openDocumentCount`) prove that closing tabs frees their documents.

## Decisions

- 2026-11-04: The owner chose "tabs within one mode only". Written without a further dialogue while the owner's goal "all planned specs implemented" was active; shortcuts and the several-documents prompt follow paint.net and recorded assumptions.
- 2026-11-04: Clarification pass settled without a dialogue: same-file rule defined (paths, `isSameEntry`, no handle = never same); recovering is not a session-replacing action (recovery lists only the mounted mode's snapshots); Save All runs in tab order; the core's open-document count is a test diagnostic (AC-16); several dropped files open as tabs (AC-19); a running save makes session-wide actions wait (AC-17).
- 2026-11-04: Revises `app-shell` AC-08 (Create in the same mode adds a tab instead of remounting), `app-shell` AC-16 (the top bar shows the active tab) and `autosave-recovery` AC-05 (Recover opens a tab and keeps the dialog open); those specs carry the new wording.
- 2026-11-04: Owner: "on Mac we have different modifier key names". Added the tab-key table per platform (⌃Tab on macOS because ⌘Tab is the app switcher; ⇧⌘[ / ] as in Safari and Finder; ⌘W) and AC-20 (platform key names in hints, physical-key matching for ⌥ chords).
- 2026-11-04 (spec-build): Per-tab state behind the existing stores: `lib/shell/tab-store.ts` returns a proxy that forwards each store's per-document keys (`ed`, `view`, `play`, `file` in Pixel mode; `editor`, `view` in Image mode) to the active tab's own `$state` and the rest to the shared state. Reason: every module keeps reading `store.key`; saving, closing and autosave bind to their tab explicitly, so they stay correct across a tab switch.
- 2026-11-04 (spec-build): File ▸ New… and File ▸ Open… no longer ask before the dialog / picker; the prompt follows Create or the pick, and only when the result is another mode's document. `unsaved-changes-prompt` AC-01 and its e2e tests are reworded accordingly. Reason: a same-mode result opens a tab without a prompt (AC-02), and AC-12 wants the document read and checked before the prompt.
- 2026-11-04 (spec-build): A session-wide action during a running save waits for it instead of being ignored (AC-17 over `unsaved-changes-prompt` AC-08's last sentence, which is reworded). While the prompt is open, a save from it runs or an action waits, every shell routing is ignored, same-mode opens included. Reason: AC-17; the prompt's answer applies to the action it names (`unsaved-changes-prompt` AC-08).
- 2026-11-04 (spec-build): `EditorProps.confirmUnsaved` is replaced by `confirmClose(doc, close)` (closing one tab asks about that document only), plus `registerSession(session) => unregister` (the shell routes same-mode documents to `EditorSession.open` / `create`) and `onEmpty(error?)` (last tab closed, or the first document failed: the start screen, with the error). `EditorDocument` gains `activate()`; every tab registers its own `EditorDocument`. Reason: the shell's single prompt serves one tab, several tabs and the desktop close.
- 2026-11-04 (spec-build): `AutosaveSession` is now one per document (its constructor takes the identity); the Recovery list moved to a new `RecoveryOffer` per editor. `finish()` waits for a snapshot write in flight before removing the snapshot (edge case "closing a tab while an autosave write of it is running").
- 2026-11-04 (spec-build): The open-document count (AC-16) is exported by the cores as `document_count()` (`pincel-image-wasm`, the handle map's size) and `openDocumentCount()` (`pincel-wasm`, a per-thread live counter in `Document`), and published for tests on `globalThis.__pincelDiagnostics.openDocuments.{pixel,image}`. Reason: the spec asks for a core-level diagnostic; a global hook is how the e2e reads it without importing the hashed wasm chunk.
- 2026-11-04 (spec-build): Same file: the path comparison folds case where the user agent is Windows or macOS (the desktop app runs on the OS it reports). A PNG opened in Pixel mode saves to a new `.aseprite` and has no path, so opening that PNG again opens a second tab ("no handle = never the same file").
- 2026-11-04 (spec-build): The window title is `document.title`, now set by Image mode as well (`● name – Pincel`, as Pixel mode did). The desktop window's native title is not synced — unchanged by this spec.
- 2026-11-04 (spec-build): Tab switching is blocked while a dialog is open because the dialogs are modal overlays above the tab bar and the editors' key handlers return early while one is open; the tab being left drops its gestures, playback and sub-modes (Pixel: polygon, stamp, tile editor; Image: gesture, previews).
- 2026-11-04 (spec-build): Pixel-mode Save no longer sets the editor-wide `file.busy`; the tab's own running save is what blocks closing it and autosaving it, so other tabs stay usable during a save (AC-17).
- 2026-11-04 (spec-build): Several dropped files: an unsupported one among them is skipped (its error shows unless the skipped-files notice replaces it); the notice reads "{n} dropped file(s) of the other mode were not opened". Files dropped on the start screen keep today's behavior (the first one). An OS hand-over that arrives while the previous one is still being opened is dropped, as before this spec.
